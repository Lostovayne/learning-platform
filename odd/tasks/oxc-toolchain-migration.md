# oxc toolchain migration (oxfmt + oxlint)

Objective: replace ESLint with oxlint and install oxfmt as the project formatter, migrating the `eslint-config-next` rule set instead of discarding it.
Branch: `chore/oxc-toolchain-migration`
Runner: `npx oxlint` / `npx oxfmt` (the project has no test runner yet)

## Specs

S1. Install the oxc toolchain. Verbatim user request:
"agregaremos del entorno de oxc , agregaremos oxfmt como remplazo de prettier para este proyecto , y agregaremos oxlint como remplazo de eslint por lo que migraremos las reglas de eslint , a oxlint"

S2. oxfmt replaces Prettier. Verbatim: "agregaremos oxfmt como remplazo de prettier para este proyecto".

- Acceptance: `oxfmt` is a devDependency with a config file, `npm run format` runs it, and it respects the repo's declared 2-space standard (`.editorconfig`).
- Note: the repo had no Prettier, so this is additive, not a migration.
- Known risk: installed `oxfmt` is `0.73.0`, still pre-1.0. Its config surface may move.

S3. oxlint replaces ESLint with FULL removal. Verbatim: "agregaremos oxlint como remplazo de eslint por lo que migraremos las reglas de eslint , a oxlint".
User decision, verbatim: "Reemplazo total de ESLint".

- Acceptance: `eslint`, `eslint-config-next` and `eslint.config.mjs` are gone; `oxlint` is the only linter; `npm run lint` runs oxlint.

S4. Rule migration is 1:1 with the real ESLint resolution, produced by oxc's own migration tool.
User correction, verbatim: "el propio oxlint tiene comandos para migrar eslint las reglas etc etc".

- Acceptance: `.oxlintrc.json` is generated by `npx @oxlint/migrate eslint.config.mjs --with-nursery` (a separate oxc package, not an `oxlint` subcommand), which preserves severities, rule options, file scoping and every rule the ESLint setup left `off`.
- Source of truth is ESLint's own resolution, read with `npx eslint --print-config <file>`: 113 rule entries, **86 active** (60 error, 26 warn) and 27 off.
- Name mapping: `@next/next/*` -> `nextjs/*`, `@typescript-eslint/*` -> `typescript/*`, `react-hooks/*` -> `react/*`. The three typescript-eslint extension rules (`no-unused-vars`, `no-array-constructor`, `no-unused-expressions`) map onto oxlint's core rules of the same name; oxlint has no `typescript/` twins for them.
- Acceptance: oxlint activates the 80 rules that ESLint had active, and `"categories": { "correctness": "off" }` stops oxlint from switching on rules ESLint never had.

S5. Accepted coverage loss, explicitly decided by the user after being shown the evidence. Six active rules have no oxlint implementation and are dropped:

- `nextjs/no-location-assign-relative-destination` (warn) - "Not implemented" per the migration tool.
- `react/no-deprecated` (error) - oxlint implements it as `typescript/no-deprecated`, behind `--type-aware`.
- `react/jsx-uses-react` (error) - obsolete with the React 17+ JSX transform.
- `react/jsx-uses-vars` (error) - covered by `no-unused-vars`, which already counts JSX usage.
- `react-hooks/config` (error) - React Compiler options are not configurable in oxlint.
- `react-hooks/gating` (error) - React Compiler gating is not configurable in oxlint.
- Acceptance: the loss is recorded in the repo (config header + README), never silent.

S6. React Compiler coverage is preserved. 14 of the 16 `react-hooks/*` rules exist in oxlint and must be enabled explicitly at their original severity, because oxlint ships them experimental and off by default.

S7. `npm run lint` exits 0 on the current codebase, and `npm run format:check` passes.

S8. Scope discipline: a tooling migration must not change which checks run. Bundling extra rules into it would make unrelated future edits fail lint for reasons the author never enabled.

- Acceptance: no rule is active in oxlint that was not active in ESLint, except the deliberate additions enumerated in S9.

S9. Deliberate additions beyond the ESLint parity set, authorized one by one.

- `no-restricted-properties` (error) rejects any `.reload()` call, so Client Components navigate with `useRouter().push()` instead of a full page reload. Nothing in the old ESLint config covered `location.reload()`.
- Acceptance: every addition is recorded in the config header and in the README, and each one is verified with a fixture that produces no finding before the addition and the expected finding after it.

## Log

L1 (user, verbatim): "agregaremos del entorno de oxc , agregaremos oxfmt como remplazo de prettier para este proyecto , y agregaremos oxlint como remplazo de eslint por lo que migraremos las reglas de eslint , a oxlint"

L2 (user decision, verbatim, after being shown the coverage evidence): "Reemplazo total de ESLint"

L3 (evidence, verified against the real artifacts, not from memory):

- `oxlint` latest is `1.88.0`; `oxfmt` latest is `0.73.0` (pre-1.0).
- oxlint ships built-in plugins covering every plugin `eslint-config-next` uses: `react` (from eslint-plugin-react + react-hooks + react-refresh + React Compiler), `nextjs` (from `@next/eslint-plugin-next`), `typescript`, `jsx-a11y`, `import`, `unicorn`.
- `react` and `nextjs` are OFF by default in oxlint and must be enabled per project.

L4 (evidence, coverage measured by feeding the config to `oxlint --print-config` and reading oxlint's own rejection list):

- oxlint accepts the mapping for `nextjs/*`, `typescript/*`, `react/*` (including the React Compiler rules), `jsx-a11y/*`, `import/*` and the core rules.
- oxlint rejects exactly nine names: the six losses in S5 plus three rules `eslint-config-next` already had turned off (`react/prop-types`, `no-dupe-args`, `no-new-symbol`), so those three cost nothing.

L5 (decision, tooling): kept `.oxlintrc.json` (JSON with comments) rather than `oxlint.config.ts`, because the oxc docs mark JavaScript/TypeScript config files experimental.

L6 (user correction, verbatim): "el propio oxlint tiene comandos para migrar eslint las reglas etc etc"

L7 (evidence, the user was right in substance): `oxlint` 1.88.0 has no `--migrate` flag and no `migrate` subcommand; `npx oxlint migrate` is read as a path and answers "No files found to lint". The official tool is the separate `@oxlint/migrate` package: `npx @oxlint/migrate [config]`, with `--output-file`, `--merge`, `--with-nursery`, `--replace-eslint-comments`, `--type-aware`, `--js-plugins` and `--details`. Running it needs the target config's imports to resolve (`eslint`, `eslint-config-next`, and `next`), so it was run in a scratch directory holding the flat config recovered with `git show 3192625:eslint.config.mjs`.

L8 (three defects found in the first, hand-written config, measured against the official output):

- It left oxlint's default `correctness` category on, so oxlint activated **192** rules where ESLint had 86. That includes rules ESLint deliberately had `off`: typescript-eslint disables the core duplicates (`no-unreachable`, `getter-return`, `constructor-super`, `no-redeclare`, ...) because TypeScript already reports them, and the hand-written config re-enabled all of them.
- Proof it was a new gate, not a migration: on one fixture the official config produced 8 findings, all from the ESLint set, and the hand-written one produced 10. The two extras were `jsx-a11y/click-events-have-key-events` and `jsx-a11y/no-static-element-interactions`, which ESLint never had active.
- It dropped the ESLint `ignorePatterns`, and used `typescript/no-unused-vars`-style names where oxlint keeps the core names.
- No rule options were lost: every rule in the ESLint resolution carries a bare severity, so the earlier worry about dropped options was unfounded.

L9 (decision, S8): regenerate the config with the official tool and add back only the vendored-directory excludes the tool cannot know (`.agents/**`, `agent/**`, `.atl/**`). Measured with `--debug=files`: without them oxlint lints 120 files, **117 of them third-party templates** under `.agents/skills/`; with them, 3 files, which is this project's own code. `--with-nursery` keeps `react/require-render-return`, a nursery rule ESLint enforced.
